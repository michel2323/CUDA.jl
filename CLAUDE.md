# cuSOLVER: applying Q from a QR factorization

Notes for working on the QR routines in `lib/cusolver/src/dense.jl` and
`lib/cusolver/src/dense_generic.jl`. Everything below was measured against
cuSOLVER 12.2.6 (CUDA 13.3) on an RTX 4080.

## What NVIDIA actually provides

cuSOLVER's "generic" 64-bit API (`cusolverDnX*`) covers the factorizations —
`Xgetrf`/`Xgetrs`, `Xpotrf`/`Xpotrs`, `Xgeqrf`, `Xsytrs`, `Xtrtri`, the eigen/SVD
family — but it has **never** gained `Xormqr` or `Xorgqr`. Confirmed by symbol dump:

```console
$ nm -D --defined-only libcusolver.so.12 | grep -iE 'ormqr|orgqr|unmqr|ungqr|larft|larfb'
cusolverDnSormqr, cusolverDnDormqr, cusolverDnCunmqr, cusolverDnZunmqr   # legacy only
cusolverDnSorgqr, cusolverDnDorgqr, cusolverDnCungqr, cusolverDnZungqr   # legacy only
cusolverDnXlarft, cusolverDnXlarft_bufferSize                            # the way out
```

There is no `Xlarfb` either. So you can factorize a matrix of any size with 64-bit
integers, but the library gives you nothing to *use* the resulting Q with. Re-run
that `nm` before assuming this is still true — if NVIDIA ever ships `Xormqr`, the
blocked code below should be replaced by a thin wrapper around it.

## The actual failure mode — it is not 32-bit dimensions

The obvious theory ("matrices over 2^31 elements overflow `int`") is **wrong**, and
chasing it wastes time. For a 65536×65536 problem `m`, `n`, `k` and `lda` all fit in
`Cint` comfortably. What overflows is the **workspace**: `cusolverDn{S,D,C,Z}ormqr_bufferSize`
returns its size *in elements* as a `Cint`, and that workspace grows like `O(m*k)`.

Measured cliff for a square problem (`m = n = k = N`, `bufferSize` query only):

| N       | result                              |
|---------|-------------------------------------|
| 32575   | ok, **2,147,377,248** elements      |
| 32576   | `CUSOLVER_STATUS_INVALID_VALUE`     |

(`typemax(Cint)` = 2,147,483,647.) So cuSOLVER refuses anything past ~32500²
*regardless of available device memory*. Two consequences worth internalising:

- The cap depends on `k`, only weakly on `n`. `ormqr_bufferSize(m=65536, n=65536,
  k=64)` succeeds fine; it is a large `k` that kills you.
- Well below the cliff the legacy routine is already a memory hog: at 32575² in
  Float64 it wants **17 GB of scratch for an 8.5 GB matrix**. An unexplained
  "Out of GPU memory" during `Q'*A` is usually this, not the operands.

`orgqr`'s workspace is far smaller (~`384*n`) and its query still succeeds at 2^18,
so it has no measured cliff. The `lda * n > typemax(Cint)` guard in `orgqr!` is a
*conservative, unverified* bound on what a 32-bit-indexed routine can address — it
has never been observed to be necessary. Do not present it as a known limit.

## The implementation

`Xormqr!` and `Xorgqr!` in `lib/cusolver/src/dense_generic.jl` are blocked
Householder (compact WY) drivers built on `larft!` + `larfb!`, needing only
`O((m + n) * blocksize)` scratch. `larfb!` is ours — cuSOLVER has no `Xlarfb` — and
is pure cuBLAS GEMM/TRMM, which already dispatch to the `_64` entry points.

`ormqr!` and `orgqr!` in `lib/cusolver/src/dense.jl` probe the legacy `bufferSize` with the
`unchecked_*` variant (generated by GPUToolbox's `@checked`, returns the status
instead of throwing) and hand the problem to the blocked path when cuSOLVER refuses.
Small problems keep hitting NVIDIA's tuned kernels unchanged. That probe is the
*exact* predicate — do not replace it with a size heuristic, because the workspace
formula is undocumented and version-dependent.

### Invariants to preserve

- **`geqrf!` leaves R in the upper triangle of the reflector panel**, while `larft!`
  and `larfb!` need V unit lower trapezoidal. You therefore cannot hand a view of `A`
  straight to `larft!`; the drivers copy the panel and call `unit_lower_triangular!`
  on its leading square block. The copy costs one pass over the matrix in total and
  is nowhere near the bottleneck.
- **`larft!` with `direct='F'` leaves the strict lower triangle of `t` undefined.**
  `t` may only ever be a TRMM *triangular operand*, never a general GEMM/copy source.
  This is why `Xorgqr!` forms `Y = t * V1ᴴ` by copying `V1ᴴ` and TRMM-ing by `t`,
  rather than the other way round. Getting this backwards produces plausible-looking
  garbage that small tests can miss.
- **Block ordering.** `Q = H(1) H(2) ... H(k)`, so `Qᴴ*C` and `C*Q` consume blocks
  front to back while `Q*C` and `C*Qᴴ` go back to front:
  `forward = (side == 'L') ⊻ (trans == 'N')`.
- **`direct='B'` is unsupported** throughout (the pre-existing `larft!` test skips it
  too). `storev='R'` likewise.
- **cuBLAS TRMM in-place (`C === B`) is supported** and the drivers rely on it; there
  is a test for it. If that ever regresses, the fix is a second workspace, not a
  reshuffle of the algorithm.
- `trans='C'` on real types is mapped to `'T'`. cuSOLVER accepts both; **CPU LAPACK
  rejects `'C'` for real matrices**, so tests comparing against `LAPACK.ormqr!` must
  translate before calling the reference.
- `larft!`, and hence everything above, needs cuSOLVER ≥ 11.6 (CUDA 12.4). Guard new
  entry points with `has_blocked_householder()`.

### Block size

`WY_BLOCKSIZE = 128`, overridable per call via the `blocksize` keyword. Larger blocks
amortise the per-block `larft!` and kernel launches, but `larft!` itself costs
`O(m*k*blocksize)`, so there is an optimum. Measured on an RTX 4080, `m = k = 8192`:

| | best nb | nb=128 vs cuSOLVER legacy |
|---|---|---|
| Float32 | ~512 | ≈ parity |
| Float64 | ~128 | ≈ parity (slightly faster) |

At `nb=128` the blocked path is within a few percent of the legacy routine while
using ~130× less scratch (2.05 GiB → 0.016 GiB at 16384² Float32). Note the RTX 4080
has 1/64 FP64 throughput; on a datacenter GPU the Float64 curve should resemble the
Float32 one and favour larger blocks. **Re-tune `WY_BLOCKSIZE` on the target hardware
before treating the default as settled.**

## Reproducing on a small GPU

You do not need a 140 GB card. The workspace cliff is driven by `m*k`, so a tall
skinny factorization with a narrow right-hand side trips it in under 6 GiB:

```julia
m, k, n = 65536, 24000, 8          # A is 5.86 GiB in Float32
F, tau = cuSOLVER.geqrf!(CUDA.randn(Float32, m, k))
C = CUDA.randn(Float32, m, n)
cuSOLVER.ormqr!('L', 'T', F, tau, C)   # legacy query fails here -> blocked path
```

Validate without a CPU reference by round-tripping (`Q * (Qᴴ * C) == C`, since Q is
orthogonal), or transfer `F`/`tau` to the host and compare against
`LinearAlgebra.LAPACK.ormqr!`.

The unit tests in `lib/cusolver/test/dense_generic/factorizations.jl` cover all four element
types, tall/wide/square, both sides, both `trans`, block sizes below/at/above `k`,
and matrix and vector `C`, all against CPU LAPACK — plus agreement between the
blocked and legacy implementations.

## Known gaps

- `LinearAlgebra.qr!(::CuMatrix)` in `lib/cusolver/src/linalg.jl` still calls the **legacy 32-bit
  `geqrf!`**, not `Xgeqrf!`. The buffer-size query succeeds up to at least 2^18, but
  whether legacy `geqrf` *computes correctly* past 2^31 elements has not been
  verified here. Switching the default factorization path needs its own benchmarking.
- `lib/cusolver/test/sparse.jl`'s `csrlsvchol!` tests are intermittently flaky and
  unrelated to any of the above; they pass on rerun in isolation.
